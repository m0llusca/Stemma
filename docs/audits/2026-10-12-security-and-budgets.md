## JavaScript

До изменений замерена настоящая production-сборка исходного master. Snapshot `apps/web/budgets/route-baseline.json` содержит source commit, SHA-256 исходного lockfile, версии среды и размеры/хеши emitted chunks. Это исходная сборка до исправлений, а не baseline, переписанный по результату.

Лимиты не увеличены: shared delta 0; reports +45 KiB; dashboard/coaching +10 KiB; **полная** транзитивная цепочка rich-графиков максимум 70 KiB. В измерение входят физические чанки зависимостей и bootstrap, а не только дополнительный код графиков.

Recharts сохранён во всех графиках. Вместо замены библиотеки выполнены:

- разделение Base UI диалога и отложенного cmdk-контента;
- перенос command handlers в отложенный компонент;
- отделение чистого URL-парсера от репозитория, импортирующего БД;
- небольшая клиентская граница Recharts при сохранении серверного расчёта sparkline;
- настройка documented Turbopack chunking и отключение scope hoisting, чтобы графики не требовали объединённые с посторонним UI модули.

У этого chunking есть компромисс: файлы меньше и лучше переиспользуются, но число запросов на отдельных маршрутах может вырасти. Проверка байтов не заменяет измерение LCP/INP на реальном трафике. Полный лабораторный throttled performance test не объявляется пройденным.

## Дополнительно найденная ошибка обновления БД

Миграция `20261007120000_backfill_calibration_review_session` из исходного master падала на существующей verify-базе с PostgreSQL 23505. Старый NULL-review мог совпасть с уже занятой уникальной комбинацией session/conversation/reviewer; несколько NULL-review также могли конкурировать за одну комбинацию.

Backfill исправлен: привязка выполняется только для единственной кандидатуры и незанятой комбинации. Неоднозначные/дублирующиеся оценки остаются NULL, без выбора победителя по догадкам. Транзакция и блокировка Review защищают от параллельных записей во время backfill.

Исправлен SQL самой ранее ошибочной миграции: новая последующая миграция не может выполниться раньше падающей. **Для БД, где старый SQL уже успешно применён, файл не будет применён повторно, но его checksum отличается от записанного — это нужно учитывать при сверке истории в `migrate dev`.** Автоматически переписывать ledger таких БД этот патч не пытается.

На выделенной `qc_app_demo_verify` неудачный запуск помечен rolled-back и исправленная миграция применена повторно. Основная база разработчика и production не менялись. Три PostgreSQL-регрессии проверяют занятую комбинацию, дубликаты и единственную валидную кандидатуру.

Только если в целевой БД уже есть **неудачный** запуск именно этой миграции, после проверки его состояния применяется обычный [порядок восстановления Prisma v6](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/patching-and-hotfixing#failed-migration):

```sh
npx prisma migrate resolve --rolled-back 20261007120000_backfill_calibration_review_session
npm run db:deploy
```

Это не команда для успешно применённых миграций и не инструкция сбрасывать БД.
